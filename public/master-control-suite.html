Local code & access

  • Search for accidental secretsUse your code editor’s project-wide search to check for hardcoded IPs, API tokens, and passwords. Never put secret values in HTML, browser JavaScript, logs, or public issues.
  • Check environment-file exclusionsConfirm local .env files are excluded by .gitignore. Keep production values in server-side Vercel environment variables and review deployment logs before sharing them.
  • Review Vercel accessEnable MFA and review project/team members and their roles. Remove access only for people who no longer need it.
  • Review Cloudflare credentialsUse least-privilege API tokens. Revoke tokens that are confirmed unused or exposed; rotate a credential suspected compromised after checking which services depend on it.
  • Audit server accessReview active admin sessions and the origin’s SSH authorized keys. Keep only recognized keys and restrict SSH to a trusted network or access gateway where practical.

DNS, tunnel & origin

  • Review DNS record by recordUse Cloudflare DNS to confirm web A/CNAME targets. Proxy only supported web records intended to use Cloudflare; keep MX and mail records DNS-only when required by the mail provider.
  • Check stale and DNS-only hostnamesReview subdomains you control and remove records that are no longer needed. A DNS-only web hostname can reveal its target; do not change mail or third-party records without confirming their purpose.
  • Limit tunnel routesExpose only required hostnames and services, use a final catch-all deny/404 route, and log/alert on rejected requests. This page describes the policy; it does not configure the tunnel.
  • Minimize origin exposureA Cloudflare Tunnel connector makes outbound connections. If you rely on the tunnel, do not expose origin web ports publicly unless separately required. For direct proxied origins, configure firewall rules for Cloudflare’s current published ranges and preserve a secure admin path.
  • Restrict SSH and review logsAllow SSH only from a trusted fixed address or access gateway where feasible. Review authentication logs for patterns; isolated failed logins can be routine internet noise. Use Fail2Ban only when appropriate for the host and service.

Authorized tunnel inventory

  • Inspect only systems you administerOn Linux, pgrep -af 'cloudflared|ngrok|ssh' can list matching processes and sudo ss -tulpn can list listening sockets. On macOS, use Activity Monitor or sudo lsof -nP -iTCP -sTCP:LISTEN.
  • Windows checksUse Task Manager’s Details tab to review processes. In an elevated Command Prompt, netstat -ano | findstr LISTENING lists listening ports and process IDs.
  • Verify before actingProcess names and open ports alone do not prove unauthorized access. Check the service configuration, owner, and provider account. If a service is confirmed unwanted, stop it through its service manager or provider controls—not a force-kill against an unknown process.
  • Protect command outputProcess listings may contain usernames, paths, or arguments. Review locally; redact sensitive details before sharing.

Device & physical safety

  • Protect devicesUse automatic screen locking, current security updates, MFA, and a private screen when viewing credentials.
  • Use normal property checksSecure doors and windows with your usual routine; maintain lighting and alarms according to household needs. Do not enter drains, culverts, utility tunnels, or other confined spaces.
  • Leave infrastructure to professionalsDo not approach or investigate utility access points or suspected underground structures. Contact the utility, property manager, or local authorities from a safe location if there is a specific hazard; use official utility maps for permitted planning work only.
  • Prioritize immediate safetyDo not confront anyone. Move to a safe place and contact a trusted person or local emergency services if there is an immediate personal safety concern.
